# V5 Field Source & Data Authority Map

Status: working specification for review before production ingestion. This describes intended source strategy; it does not claim provider availability, permissions, or completeness until verified against current provider documentation and terms.

## Principles

1. Southcoast Eats owns its internal IDs, publication decisions, taxonomy, and editorial decisions.
2. A provider is evidence, not the authority for every field.
3. Track provenance at field level where practical: source, source record ID, observed time, verification state, and conflict/freshness state.
4. Unknown is not the same as false, unavailable, or confirmed absent.
5. Manual corrections outrank routine automated refreshes until deliberately revalidated or superseded; preserve the audit trail.
6. Never retain or display provider data beyond that provider's current contractual and licensing terms. Do not store full raw provider payloads by default.
7. Do not ingest demo UI values as facts. Ratings, review counts, sample distances, and sample listing content are not production data.

## Field-level source plan

| Field / concept | Preferred source strategy | Authority and validation | Missing/conflicting data behavior |
|---|---|---|---|
| Internal restaurant ID | Generated by Southcoast Eats | Stable UUID; never use a provider ID as the primary key | Never change after creation |
| Provider place ID | Foursquare and/or OSM identifiers, separately namespaced | Unique by provider + provider ID; retain only as permitted | Do not merge records on name alone |
| Restaurant name | Foursquare and OSM candidate data; direct verification where practical | Normalize for matching; preserve verified/manual correction | Queue material conflicts; do not guess |
| Brand / chain relationship | Evidence from provider listings and verified business identity | Southcoast Eats relationship decision; distinct locations remain distinct | Leave unresolved rather than merge locations |
| Physical location ID | Generated by Southcoast Eats | Stable ID for each real-world location | Do not reuse when a location changes identity |
| Street address, locality, region, postal code, country | Provider data, cross-checked where possible; direct verification when needed | Normalize and validate; geographic launch boundary is authoritative | Keep uncertain fields unknown; queue material conflicts |
| Latitude / longitude | Provider coordinates, with cross-checks where possible | Range checks, launch-boundary checks, and plausible address proximity | Do not invent coordinates; flag suspicious mismatches |
| Website | Provider data, then official-site verification when practical | Prefer a clearly official business URL; record source and observation time | Omit when unverified or conflicting |
| Phone | Provider data, then direct verification when practical | Normalize format; associate with the correct location where possible | Omit or flag conflict rather than guess |
| Cuisine | Provider categories as evidence, mapped into Southcoast Eats taxonomy | Our controlled cuisine vocabulary wins over provider labels | Unknown if evidence is insufficient |
| Restaurant type | Provider categories plus classification rules | Separate taxonomy dimension from cuisine | Do not infer from a single weak tag |
| Food specialty | Available categories and verified evidence, mapped to our hierarchy | Southcoast Eats taxonomy and classification rules | Avoid over-specific labels without evidence |
| Primary dining experience | Classification from evidence about how the business operates | Separate from cuisine and restaurant type | Unknown if ambiguous |
| Service availability (dine-in, takeout, delivery, etc.) | Provider data and verified business information where available | Store explicit states such as confirmed available, confirmed unavailable, unknown, conflicting, stale | Missing data means unknown, not unavailable |
| Opening hours | Provider data and direct verification where practical | Store freshness/verification context; consider location-specific hours | Missing hours do not mean closed |
| Price level | Provider data only if available, meaningful, and permitted | Do not infer from cuisine, photos, or neighborhood | Omit when absent or unreliable |
| Description | Verified source material or controlled editorial copy | Do not fabricate; avoid copying restricted text | Omit if there is no reliable description |
| Photos and image metadata | Provider-approved or separately licensed sources | Verify storage/display rights, attribution, source, and retention before use | No photo is required for publication |
| Featured flag | Southcoast Eats editorial choice | Never provider-derived | Default false |
| Publication status | Southcoast Eats publication rules and review | Requires reliable identity, usable in-region location, evidence of a legitimate food business, and no unresolved identity conflict likely to mislead | Keep as draft / review when criteria are unmet |
| Field verification state | Southcoast Eats evidence and review process | Separate verification from confidence and freshness | Use explicit states; do not encode uncertainty as false |
| Field provenance | Provider observation, manual verification, owner input, or other permitted evidence | Record field name, source type/name, source record, observation time, and current/historical status | Preserve history when a value changes |
| Distance | Calculated from coordinates and the active reference location | Runtime calculation; not a provider fact | Hide when coordinates/reference location are unavailable |
| Ratings / reviews | Deferred pending a reliable source and clear usage rights | No demo ratings in production | Do not display until explicitly approved |
| Guest favorites | Browser-local state for launch | User preference, not provider data | Keep independent of restaurant-source ingestion |
| Account favorites | Supabase favorites table only if/when account favorites are implemented | Authenticated user's own rows only | Not required for guest launch |
| Discovery coverage / request usage | Southcoast Eats pipeline telemetry | Track provider, geographic cell, run status, counts, limits, retries, and timestamps | Failed/incomplete runs must never count as complete coverage |

## Provider verification gate

Before production use, record current answers for each provider/API endpoint:

- Access tier, free quota, rate limits, result caps, pagination behavior, and request costs.
- Permitted caching, persistence, refresh, derived data, and cross-provider combination.
- Required attribution and display requirements.
- Restrictions on photos, descriptions, coordinates, and other individual fields.
- Retention/deletion obligations after access ends or data changes.
- Geographic and commercial-use restrictions.

OpenStreetMap data licensing and the policies of any public OSM API are separate questions. Foursquare API access and stored-data rights must be checked against the current plan and terms. Do not assume either source is unlimited or universally free.

## Data model implications

The current schema is a useful foundation, but it does not yet fully encode all concepts above. Before ingestion, review whether we need:
- A brand entity and explicit restaurant-to-brand relationship.
- Location-specific contact details, website, hours, and service availability.
- Controlled taxonomy tables for cuisine, restaurant type, specialty, and dining experience.
- Field evidence/verification state, freshness, conflicts, and manual-correction audit.
- Photo source, license/permission basis, attribution, and retention metadata.
- Geographic discovery cells, discovery runs, and provider usage ledger.

Do not expand the schema blindly: finalize field definitions and provider constraints first, then add a focused migration.
